Environments

One codebase, many copies of your infrastructure.

You want dev to experiment in and prod for customers, built from the same code so they don’t drift apart.

Terraform codeone module
devits own state
prodits own state

The real question: how do we keep their state separate, so working on dev can never touch prod?

Environments

Workspaces vs a folder per environment.

Workspaces 
$ terraform workspace new prod
$ terraform workspace select dev
  • Same code, same backend, same credentials
  • Current workspace is invisible: one wrong select and you apply to prod
  • Differences become terraform.workspace == "prod" ? …

Good for: short-lived copies, like a feature branch.

Folder per environment
environments/ ├── dev/ # own backend + tfvars └── prod/ # own backend + tfvars
  • Your path tells you where you are
  • Prod gets its own state bucket, IAM role and approvals
  • Differences are explicit in terraform.tfvars

Our default. Strongest: one AWS account per environment.

Environments

Thin environments, shared logic.

infra/ ├── modules/ │ └── web-app/ # the logic └── environments/ ├── dev/ │ ├── backend.tf │ ├── main.tf │ └── terraform.tfvars └── prod/ ├── backend.tf ├── main.tf └── terraform.tfvars
prod/backend.tf
terraform {
  backend "s3" {
    bucket       = "bootcamp-tfstate-prod"
    key          = "web-app/terraform.tfstate"
    use_lockfile = true
  }
}
prod/main.tf
module "web_app" {
  source        = "../../modules/web-app"
  environment   = "prod"
  instance_type = "t3.small"
}

The duplicated files are thin on purpose: the logic lives once, in the module.

Lifecycle rules

Terraform’s defaults aren’t always safe.

The defaults are reasonable for most resources. For some, they’re dangerous.

It destroys first

When a change can’t happen in place, the old resource is deleted before the new one exists.

It undoes every difference

Anything changed outside Terraform is treated as drift and reverted.

It will delete anything

Databases, state buckets, encryption keys: all are just resources to Terraform.

The lifecycle block overrides this, one resource at a time
Lifecycle rules

Three rules you’ll use most.

prevent_destroy

For things that must never be deleted by accident.

lifecycle {
  prevent_destroy = true
}

Watch out: delete the whole block and the protection goes with it.

create_before_destroy

When downtime during a replacement matters.

lifecycle {
  create_before_destroy = true
}

Watch out: both copies exist briefly. Unique names clash; use name_prefix.

ignore_changes

When something outside Terraform legitimately changes a value.

lifecycle {
  ignore_changes = [tags, tags_all]
}

Watch out: every ignored attribute is drift you chose not to see.

Ordering

depends_on: a dependency Terraform can’t see.

Terraform orders work by references. If a dependency isn’t a reference, you have to say it.

module.vpc
public_subnets
internet gateway
route to the internet
aws_instance.webruns dnf install httpd
resource "aws_instance" "web" {
  subnet_id = module.vpc.public_subnets[0]
  # ...

  depends_on = [module.vpc]

  lifecycle { ... }
}

depends_on sits next to lifecycle, not inside it.

Use it only for real, invisible dependencies. It makes Terraform more cautious and plans show more “known after apply”.

Guardrails

Check before you act, check what you got.

plan
preconditionchecks inputs
create / change
postconditionchecks real values

precondition

precondition {
  condition     = data.aws_ami.al2023.architecture == "x86_64"
  error_message = "t3 instances need an x86_64 AMI."
}

Fails the plan with your message, before AWS returns a confusing error mid-apply.

postcondition

postcondition {
  condition     = self.root_block_device[0].encrypted
  error_message = "Root volume must be encrypted."
}

Uses self. Checked at plan if the value is known, otherwise right after apply.

Both live inside the lifecycle block. A failed postcondition during apply means the resource exists, but nothing is built on top of it.

Safe refactoring

moved: rename without destroying.

Rename the resource, then tell Terraform
resource "aws_instance" "app" {  # was "web"
  # ... unchanged ...
}

moved {
  from = aws_instance.web
  to   = aws_instance.app
}

Also works into a module: to = module.web_app.aws_instance.this

Without moved
Plan: 1 to add, 0 to change, 1 to destroy.
With moved
aws_instance.web has moved to aws_instance.app
Plan: 0 to add, 0 to change, 0 to destroy.

Keep moved blocks for a while: other environments may not have applied yet.

Safe refactoring

import: adopt what was clicked into existence.

import {
  to = aws_s3_bucket.clickops
  id = "bootcamp-dev-clickops-rs"
}
$ terraform plan -generate-config-out=generated.tf
Plan: 1 to import, 0 to add, 0 to change, 0 to destroy.

Checklist

  • The id format differs per resource: see the Import section of its provider docs
  • Generated config is a starting point: clean it up
  • Apply only when the plan shows the import and no changes
  • import blocks live in the root module (the environment folder)
Safe refactoring

removed: let go without deleting.

Handing a resource to another team or project? Remove it from your state, keep it in AWS.

Replace the resource block with
removed {
  from = aws_s3_bucket.clickops

  lifecycle {
    destroy = false
  }
}

Replaces the older terraform state rm. Needs Terraform 1.7+.

Just delete the resource block

Terraform plans to destroy the bucket.

Use a removed block

Gone from terraform state list, still in the S3 console.

Wrap-up

Every change goes through code and a reviewed plan.

Including changes to how Terraform tracks your infrastructure.

Hard to hit the wrong env

A folder, and ideally an account, per environment.

Dangerous changes are explicit

Lifecycle rules, preconditions and postconditions say what’s allowed.

No state surgery

moved, import and removed are reviewed in a pull request.
