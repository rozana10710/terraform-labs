THE PROBLEM

Hardcoding doesn't scale

Lab 2 works once. Change the region, the owner or the environment and you rewrite the code.

BEFORE · HARDCODED
resource "aws_instance" "web" {
  ami           = "ami-0abc1234def567890"
  instance_type = "t3.micro"

  tags = {
    Owner = "rosanna"
    Env   = "dev"
  }
}
AFTER · REUSABLE
resource "aws_instance" "web" {
  ami           = data.aws_ami.al2023.id
  instance_type = local.instance_type

  tags = local.common_tags
}

# same code → dev, prod, every student
Same code, different inputs.

INPUT VARIABLES

Variables are your inputs

Like function parameters: the code stays the same, the values change.

variable "environment" {
  description = "Deployment environment"
  type        = string
  default     = "dev"

  validation {
    condition     = contains(["dev", "prod"], var.environment)
    error_message = "Must be dev or prod."
  }
}

# use it:  var.environment
  • description

    Explains the variable to whoever uses your code

  • type

    string · number · bool · list · map · object

  • default

    Optional. Without it, the value is required

  • validation

    Rejects bad values at plan, before AWS

Prod lens: validate early. A typo like "prd" fails at plan, not in AWS.

VARIABLE PRECEDENCE

Who wins when values conflict?

Terraform reads values from several places. The later one in this list overrides the earlier ones.

WEAKESTSTRONGEST
1default

In the variable block

2TF_VAR_name

Environment variable

3terraform.tfvars

Loaded automatically

4*.auto.tfvars

Alphabetical order

5-var / -var-file

Command line

Surprise: TF_VAR_ loses to terraform.tfvars.

SECRETS

Handling secrets safely

Two rules: secrets never live in your code, and the state file must be protected.

NEVER

Secrets in .tfvars

If the file is committed, the secret is in Git history forever.

DO

Read from SSM

data "aws_ssm_parameter" "db" {
  name = "/app/prod/db_pass"
}

# value read at runtime
REMEMBER

sensitive = true

Hides values from CLI output. The state still stores them in plain text.

Prod lens: sensitive ≠ encrypted. Keep state in a private, encrypted S3 bucket.

LOCALS

Locals: write once, reuse

A named value you calculate inside your code, so you never repeat yourself.

VARIABLE

Input the user gives

owner = "rosanna"

Ingredients handed to you

LOCAL

Value you build inside

local.common_tags

What you prep in your kitchen

Rule of thumb: if the user sets it, it's a variable. If you derive it, it's a local.

locals {
  common_tags = {
    Owner       = var.owner
    Environment = var.environment
    ManagedBy   = "terraform"
  }
}

# reuse everywhere
tags = local.common_tags
Change it in one place, every resource follows.

DATA SOURCES

Read, don't create

A data source asks AWS for information that already exists. Nothing gets created.

  1. Your code

    data "aws_ami"

  2. AWS API

    Finds latest AL2023

  3. aws_instance

    Uses the AMI ID
data "aws_ami" "al2023" {
  most_recent = true
  owners      = ["amazon"]

  filter {
    name   = "name"
    values = ["al2023-ami-2023.*-x86_64"]
  }
}

# use it:
ami = data.aws_ami.al2023.id
No hardcoded IDs: AMIs differ per region and change over time.

COUNT VS FOR_EACH

Position vs name

Both create many copies. The difference is how Terraform tracks them. Remove "red" and see.

COUNT · BY POSITION
BEFOREAFTER REMOVING "red" [0] red[0] greenreplace[1] green[1] bluereplace[2] blue[2] —destroy

2 replaced, 1 destroyed

FOR_EACH · BY NAME
BEFOREAFTER REMOVING "red" ["red"]["red"]destroy["green"]["green"]unchanged["blue"]["blue"]unchanged

Only 1 destroyed

Prod lens: prefer for_each with stable keys. Use count only for on/off.

EXPRESSIONS

Conditionals and for expressions

Small pieces of logic that make one configuration behave differently per environment.

CONDITIONAL · IF / ELSEcondition ? if_true : if_false
is_prod = var.environment == "prod"

instance_type = local.is_prod ? "t3.small" : "t3.micro"

# on/off switch with count
count = local.is_prod ? 1 : 0

Bigger server and an alarm, only in prod.

FOR · TRANSFORM A LIST[for item in list : change(item)]
[for name in ["logs", "data"] : upper(name)]
→ ["LOGS", "DATA"]

{ for k, b in aws_s3_bucket.this : k => b.bucket }
→ { logs = "bootcamp-rosanna-logs", ... }

Pick up each apple, peel it, put it in a new basket.

for_each creates resources. for only builds values.

FUNCTIONS

Built-in helpers

Terraform ships with many functions. These six cover most of what you'll write.

lower("Rosanna")→ "rosanna"
length(["a", "b"])→ 2
contains(["dev","prod"], "dev")→ true
merge({a=1}, {b=2})→ {a=1, b=2}
join("-", ["web","dev"])→ "web-dev"
keys({logs="x", data="y"})→ ["data","logs"]
TRY IT FIRST
$ terraform console
> lower("Rosanna")
"rosanna"
> merge({a=1}, {b=2})
{ "a" = 1, "b" = 2 }
> exit

No AWS resources created.

Test any expression in terraform console before using it in code.

PROD LENS

Four rules for production

01

for_each with stable keys

count index shifts can destroy resources you didn't touch.

02

Validate inputs early

Fail at plan with a clear message, not halfway through apply.

03

No secrets in .tfvars

Read them from Secrets Manager or SSM at runtime.

04

sensitive ≠ encrypted

Values sit in state as plain text. Lock down the state bucket.
