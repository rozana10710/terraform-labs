The problem

Three environments. Three copies. One bug.

Your team needs the same web server in dev, test and prod. Without modules, you copy the code.

dev/main.tfsecurity group + EC2
test/main.tfsecurity group + EC2 (copied)
prod/main.tfsecurity group + EC2 (copied)
Someone finds port 22 open to the internet. Now you fix it in three places, and someone will forget one.

The solution

A module is just a folder of .tf files.

Write the code once, use it many times. Fix it once, and every place that uses it gets the fix.

modules/web-serverwritten once
↓   ↓   ↓
devname = "dev"
testname = "test"
prodname = "prod"

Think of it as a recipe: write it once, then only say what changes each time.

Root module

Where you run init, plan and apply. Holds the provider and the backend.

Child module

A folder the root module uses with a module block. It has no provider block of its own.

Using a module

Same recipe, different values.

module "web_dev" {
  source = "./modules/web-server"

  name      = "dev"
  subnet_id = "subnet-0abc..."
}

module "web_prod" {
  source = "./modules/web-server"

  name      = "prod"
  subnet_id = "subnet-0def..."
}

source tells Terraform where the module lives.

Everything else is the module's inputs: only what changes each time.

Two web servers. Zero copied resources.

Inputs and outputs

Inputs and outputs are the module's contract.

Inputs

variables.tf

What you give the module: name, subnet_id.

Outputs

outputs.tf

What it gives back: module.web_dev.instance_id.

Inside

main.tf

Hidden from callers. You don't need to know it to use the module.

Like the buttons on a microwave: you use the buttons, not the wiring. Rename a variable and you break every caller.

Module sources

Where modules come from.

Local

Your own folder

source = "./modules/web-server"

Nothing to download.

Registry

Public modules

source  = "terraform-aws-modules/vpc/aws"
version = "6.5.1"

Pin with version.

Git

Company modules

source = "git::https://gitlab.../
  web-server.git?ref=v1.2.0"

Pin with ?ref= a tag.

Added or changed a module? Run terraform init again.

Registry vs your own

Don't reinvent the VPC.

Public registry

For common building blocks

VPC, security groups, EC2. Tested by thousands of users, ready in minutes.

Big: the VPC module has 200+ inputs.

Your own

For your team's rules

Naming, tags, encryption, "our standard web service". Small and easy to read.

You decide when it changes.

In practice, teams do both: their own modules wrap public ones.

Prod lens

Four rules for real projects.

Rule 1

Pin to a tag

Never a branch. main changes every time someone pushes.

Rule 2

Keep it small

One module, one job. No "god module" that creates everything.

Rule 3

One catalog

Company modules in one place, with version numbers.

Rule 4

Read first

A public module is someone else's code in your AWS account.

Rule 1 · Pin versions

Same code today, same code tomorrow.

Don't 
source = "git::https://.../vpc.git?ref=main"

module "vpc" {
  source = "terraform-aws-modules/vpc/aws"
  # no version!
}
Do 
source = "git::https://.../vpc.git?ref=v1.2.0"

module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "6.5.1"
}
.terraform.lock.hcl locks providers only, not modules. The pin is your only protection.

Rule 3 · Module catalog

Version numbers tell a story.

Keep company modules in one place (for example a GitLab group) and tag every release.

Patch

v1.0.0 → v1.0.1

A small fix. Safe to upgrade.

Minor

v1.0.0 → v1.1.0

A new feature. Nothing breaks.

Major

v1.0.0 → v2.0.0

Something changed that can break you. Read the changelog.

Rule 4 · Read before you trust

A real surprise from the EC2 module.

module "ec2" {
  source  = "terraform-aws-modules/ec2-instance/aws"
  version = "~> 6.0"

  subnet_id = var.subnet_id

  # Without this line, the module creates its
  # security group in the DEFAULT VPC
  security_group_vpc_id = var.vpc_id
}

Version 6 creates a security group by default.

We only found out by reading the module's Inputs page.

Check what it creates, what it changes, and which versions it needs.

Dev and prod

Same code. Different settings.

environments/dev/terraform.tfvars

environment   = "dev"
vpc_cidr      = "10.10.0.0/16"
azs           = ["eu-west-1a"]
instance_type = "t3.micro"

environments/prod/terraform.tfvars

environment   = "prod"
vpc_cidr      = "10.20.0.0/16"
azs           = ["eu-west-1a", "eu-west-1b"]
instance_type = "t3.small"
main.tf is identical. Each environment has its own state file, so destroying dev can never touch prod.

If something breaks

Common errors and fixes.

ErrorFix
Module not installedRun terraform init in that folder.
Unreadable module directoryWrong source path. From environments/dev it's ../../modules/...
Unsupported argumentThe module has no such input. Check its variables.tf.
No value for required variableMissing or misspelled in terraform.tfvars.
Prod plan wants to destroy devBoth use the same state key. Fix prod/versions.tf.

Recap

What to remember.

A module is a folder of .tf files: write once, use many times.

Variables go in, outputs come out. That's the contract.

Use the Registry for building blocks, your own modules for your rules.

Always pin a version. Never ?ref=main.

Same code for every environment. Only .tfvars changes.

One state file per environment.
